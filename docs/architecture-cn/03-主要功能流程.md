# 03 主要功能流程

本篇只讲**主干链路**:每一步给出「谁调用谁」和「入口函数在哪」。细节留到各模块内部,但每条流程都保证
从头到尾可追踪,不出现「此处略」的断链。

| --- | --- |

`Main::start()` 里的关键决策:

- `--editor` / `-p` / `--project-manager` → 创建 `EditorNode` 或 `ProjectManager` 作为 `MainLoop`;

它是单测环境的初始化,调试单测时可对照阅读。

## F2 主循环(帧流程)

一帧内可能包含 **0..N 次物理步进 + 1 次逻辑帧 + 1 次渲染**。`physics/common/max_physics_steps_per_frame`
默认 8,`physics_ticks_per_second` 默认 60;`physics_jitter_fix` 用于抑制抖动。

```mermaid
sequenceDiagram
    autonumber
    participant M as Main::iteration
    participant MQ as MessageQueue
    participant ML as MainLoop SceneTree
    participant XR as XRServer
    participant P3 as PhysicsServer3D
    participant P2 as PhysicsServer2D
    participant NAV as NavigationServer2D/3D
    participant RS as RenderingServer

    M->>M: OS::get_ticks_usec() 计算 advance（含 jitter fix、time_scale）
    M->>XR: XRServer::_process()
    loop advance.physics_steps 次
        M->>MQ: 若 agile input，flush_buffered_events()
        M->>ML: iteration_prepare()（FTI 准备、RS::tick()）
        M->>P3: sync() + flush_queries()
        M->>P2: sync() + flush_queries()
        M->>ML: physics_process(physics_step * time_scale)
        Note over ML: 发 physics_frame 信号 → 剔除视图 _process_picking → _process(true)
        ML-->>M: 若返回 true 则退出
        M->>NAV: NavigationServer2D/3D::physics_process()
        M->>MQ: flush()
        M->>P3: end_sync() + step()
        M->>P2: end_sync() + step()
        M->>MQ: flush()
        M->>ML: iteration_end()（FTI 提交插值变换）
    end
    M->>RS: sync()（提交本帧所有待处理渲染命令）
    M->>ML: process(process_step)
    Note over ML: 发 process_frame 信号 → multiplayer->poll() → _process(false) → timers/tweens → 删除队列 → idle 回调
    M->>RS: draw_viewports(true)
    M->>M: EngineDebugger::iteration() / Performance 指标更新 / OS::delay 帧率限制
```

要点:

- **物理与逻辑分离**:`_physics_process` 只在物理步进里跑,`_process` 每逻辑帧跑一次;两者之间通过
  `physics_interpolation`(FTI)或节点自己的插值做视觉平滑。
- **`MessageQueue` 是本帧的「命令总线」**:`call_deferred`、`queue_free`、`queue_redraw` 都排队,
  在固定位置成批 flush,因此**释放是延迟的**(`_flush_delete_queue` 在帧末)。
- **`_process` 里创建的节点不会立刻进入树**,`add_child` 的 `_enter_tree` 通知在合适时机统一发出。
- 渲染线程模型见 `04` 的「线程模型」;`RenderingServer::sync()` 是主线程与渲染线程的交汇点。

## F3 节点生命周期与通知传播

```mermaid
stateDiagram-v2
    [*] --> 构造: 用 memnew 或 ClassDB 实例化
    构造 --> 未入树: 设置属性、_init
    未入树 --> 入树中: add_child
    入树中 --> 已入树: NOTIFICATION_ENTER_TREE（父→子递归）+ _enter_tree
    已入树 --> 就绪: NOTIFICATION_READY（子→父递归）+ _ready 只调用一次
    就绪 --> 运行: NOTIFICATION_PROCESS / PHYSICS_PROCESS 每帧
    运行 --> 退出中: remove_child 或 queue_free
    退出中 --> 未入树: NOTIFICATION_EXIT_TREE + _exit_tree
    未入树 --> 已释放: NOTIFICATION_PREDELETE + memdelete
    已释放 --> [*]
```

传播规则(容易搞反,务必记住):

| 通知 | 传播方向 | 触发时机 |
| --- | --- | --- |
| `NOTIFICATION_ENTER_TREE` / `_enter_tree` | **父 → 子** | `add_child` 后,`_ready` 前 |
| `NOTIFICATION_EXIT_TREE` / `_exit_tree` | **父 → 子** | 移除时 |
| `NOTIFICATION_READY` / `_ready` | **子 → 父** | 子树全部入树后,每节点仅一次 |
| `NOTIFICATION_PROCESS` | 逐节点 | 在 `_process` 回调前由 `SceneTree::_process` 触发 |
| `NOTIFICATION_PHYSICS_PROCESS` | 逐节点 | 物理帧 |
| `NOTIFICATION_PREDELETE` | 逐节点 | `memdelete` 前 |

- 顺序控制:同一父节点下按子节点顺序与 `process_priority`、`process_physics_priority` 排序;
- `set_process(false)` 只是不再调用回调,节点仍在树上;
- `queue_free()` 只是把释放请求投递到 `SceneTree` 的删除队列,帧末统一执行;
- 分组(group)是另一条广播通道:`call_group` / `notify_group` / `set_group`,内部有 `SceneTreeGroup` 加速。

相关文件:`scene/main/node.cpp`、`scene/main/scene_tree.cpp`。

## F4 资源加载(运行时)

```mermaid
sequenceDiagram
    autonumber
    participant U as 脚本 / 节点
    participant RL as ResourceLoader
    participant CACHE as ResourceCache
    participant RFL as ResourceFormatLoader
    participant FA as FileAccess
    participant DEP as 依赖资源

    U->>RL: load(path, type_hint, cache_mode)
    RL->>CACHE: 查缓存（含 UID 映射 ResourceUID）
    alt 命中
        CACHE-->>RL: 直接返回 Ref<Resource>
    else 未命中
        RL->>RL: _path_remap() 与 loader 查找（按扩展名/类型）
        RL->>RFL: loader->load()（可能走线程池 _run_load_task）
        RFL->>FA: open() 读取文件
        RFL->>DEP: 递归加载外部依赖（sub-thread 并行）
        RFL-->>RL: Ref<Resource>
        RL->>RL: 设置 path/UID、resolve 引用、触发 changed 信号
        RL->>CACHE: 按 cache_mode 缓存
    end
    RL->>RL: 有加载后置处理时 ResourceLoader::load_threaded_* 进度回调
```

- 加载模式 `CacheMode`:`CACHE_MODE_IGNORE` / `REUSE` / `REPLACE` / `IGNORE_DEEP` 等,决定了缓存与
  「同一路径多实例」的行为,这是排查「资源被重复加载」问题的关键。
- 线程化加载:`load_threaded_request()` → 后台 `_run_load_task` → `load_threaded_get_status()` 轮询,
  场景切换常用它做加载画面。
- 打包后:`FileAccessPack` 让路径透明地落到 PCK 中,`FileAccess` 层无感知。
- 编辑器额外有 `RemoteFilesystemClient`,让运行实例从编辑器进程拉取资源(用于「远程调试」)。

相关文件:`core/io/resource_loader.cpp`、`core/io/resource.cpp`、`core/io/resource_format_binary.cpp`。

```mermaid
sequenceDiagram

    participant EFS as EditorFileSystem
    participant IMP as ResourceImporter
    participant DISK as .godot/imported 目录
```

## F6 渲染流程

### F6.1 2D 渲染

```mermaid
sequenceDiagram
    autonumber
    participant NODE as CanvasItem / Control
    participant MQ as MessageQueue
    participant VP as Viewport
    participant RS as RenderingServer
    participant RVC as RendererCanvasCull
    participant RVR as RendererCanvasRender 后端

    NODE->>NODE: 属性变化 → queue_redraw()
    NODE->>MQ: call_deferred(_redraw_callback)
    MQ->>NODE: _redraw_callback()
    Note over NODE: canvas_item_clear + drawing=true
    NODE->>NODE: NOTIFICATION_DRAW → _draw()
    NODE->>RS: draw_rect / draw_texture / draw_multimesh ...
    RS->>RVC: canvas_item_add_*() 记录命令到 Item
    Note over VP: 帧内 viewport 收集 redraw 请求
    VP->>RS: 需要在 draw 前完成重绘
    RS->>RVR: render_canvas() → 合批（batch）→ 提交 RD/GLES3
```

要点:

- `queue_redraw` **不是立即绘制**,而是把「重绘」推迟到 `MessageQueue` flush 时执行 `_draw`,
  因此在 `_draw` 之外调用绘制 API 会报错(见 `canvas_item.cpp:56` 的断言)。
- 2D 命令在 `RendererCanvasCull` 中按材质/纹理/混合模式**排序与合批**,`draw_index`、`z_index`、
  `CanvasLayer` 决定绘制顺序。
- 后端两条路:`RendererCanvasRenderRD`(forward+ / mobile)与 `RasterizerCanvasGLES3`(gl_compatibility)。

### F6.2 3D 渲染

```mermaid
sequenceDiagram
    autonumber
    participant MAIN as Main::iteration
    participant RS as RenderingServer::draw_viewports
    participant RVP as RendererViewport
    participant SC as RendererSceneCull
    participant RSR as RendererSceneRenderRD
    participant RD as RenderingDevice
    participant DRV as RenderingDeviceDriver 图形 API 后端

    MAIN->>RS: draw_viewports(swap_buffers)
    RS->>RVP: 遍历 sorted_active_viewports
    RVP->>SC: 取 scenario / environment / camera / render_buffers
    RVP->>SC: cull 阶段：可见性、光源收集、LOD、遮挡剔除
    SC-->>RVP: PagedArray<RenderGeometryInstance*> + lights + decals + probes
    RVP->>RSR: render_scene(render_data)
    RSR->>RSR: 阴影贴图 → SDFGI/VoxelGI → 不透明 → 天空 → 透明/半透明
    RSR->>RSR: 后处理：SSAO/SSIL/SSR/DoF/色调映射/TAA/FSR
    RSR->>RD: 录制命令（RenderGraph 自动插入 barrier/依赖）
    RD->>DRV: submit() + present（或 blit 到窗口）
```

要点:

- **剔除与渲染分离**:`RendererSceneCull` 维护实例/光源/探针的注册表并产出本帧的 `PagedArray`,
  真正绘制由 `RendererSceneRenderRD` 完成;`Dummy` 后端把两者都换成空实现。
- **`RenderingDevice` 是 GPU 抽象层**:`RenderingDeviceDriver` 有两个实现族——图形 API 后端
  (`vulkan/metal/d3d12`)与不可用的 `dummy`。RD 层负责资源、命令缓冲、屏障、管线缓存。
- **`forward_plus` vs `mobile` vs `gl_compatibility`**:前两者共享 RD 与大部分存储层,差异在
  `forward_clustered/` 与 `forward_mobile/` 的场景渲染实现;`gl_compatibility` 走 GLES3 独立路径。
- 渲染线程开启时(`rendering/driver/threads/thread_model`),`RenderingServerWrapMT` 把命令写入
  `CommandQueueMT`,`RenderingServer::sync()` 是唯一的同步点。

## F7 物理流程

```mermaid
sequenceDiagram
    autonumber
    participant M as Main::iteration
    participant ST as SceneTree
    participant PS as PhysicsServer3D 及其 WrapMT
    participant DSS as PhysicsDirectSpaceState
    participant NODE as CollisionObject3D 等
    participant IMPL as 物理实现（GodotPhysics / Jolt）

    M->>PS: sync() + flush_queries()（把上一帧排队命令应用）
    M->>ST: physics_process(delta)
    ST->>NODE: NOTIFICATION_PHYSICS_PROCESS → _physics_process()
    NODE->>PS: set_transform / apply_force / move_and_slide 等
    M->>M: message_queue->flush()
    M->>PS: end_sync() → 之后命令直接生效
    M->>IMPL: step(delta)（积分、碰撞检测/求解、约束）
    IMPL->>NODE: 回调 body_* / area_* 与信号（signal）
    IMPL-->>DSS: 更新 space state（供射线/形状查询）
    M->>PS: 下一轮 sync() 时把变换回写
    Note over PS: PhysicsServer3D::sync/end_sync 是一道「命令批屏障」
```

要点:

- **`sync/flush_queries/end_sync/step` 四段式**是理解物理线程安全的关键:它们在物理步进内按序调用
  (`main/main.cpp:4965-5046`)。
- `move_and_slide()` 由 `CharacterBody3D` 在 `_physics_process` 中调用,内部使用
  `PhysicsDirectBodyState` + `KinematicCollision` 做滑动求解。
- 查询 API(`intersect_ray`、`intersect_shape`、`cast_motion`)通过 `PhysicsDirectSpaceState3D` 暴露,
  **必须在物理帧内使用**。
- 后端可替换:`godot_physics_3d` / `jolt_physics`,通过 `PhysicsServer3DManager::set_default_server`
  与项目设置 `physics/3d/physics_engine` 选择。
- 物理插值:开启 FTI 后 `SceneTree::client_physics_interpolation_*` 负责在物理步与渲染帧之间插值。

## F8 GDScript 编译与执行

```mermaid
sequenceDiagram
    autonumber
    participant RL as ResourceLoader
    participant SRF as GDScriptResourceFormatLoader
    participant PSR as GDScriptParser
    participant ANA as GDScriptAnalyzer
    participant CG as GDScriptByteCodeGenerator
    participant COMP as GDScriptCompiler
    participant GD as GDScript
    participant VM as GDScriptFunction/vm

    RL->>SRF: 加载 .gd
    SRF->>PSR: parse(source_code, path)
    PSR->>PSR: Tokenizer → 语法树（ClassNode/FunctionNode/...）
    SRF->>ANA: analyze 解析结果
    Note over ANA: 类型推断、依赖解析、内建函数解析、警告与 lint
    SRF->>CG: 生成 GDScriptFunction 指令流
    CG->>CG: 常量池、临时槽位、跳转回填（多趟 pass）
    CG->>COMP: 绑定到 GDScript 类（含内部类/静态变量）
    COMP->>GD: 写入成员表、方法表、信号表、依赖
    GD->>GD: 写入 .gd 缓存（GDScriptCache，加快下次加载）
    GD-->>RL: Ref<GDScript>

    Note over VM: 运行期
    NODE->>GD: new() / GDScriptInstance
    NODE->>VM: GDScriptFunction::call()（字节码解释执行）
    VM->>VM: 栈式指令派发，命中 GDScriptVM 的优化路径
```

要点:

- 前端三件套 `Tokenizer → Parser → Analyzer`,后端 `ByteCodeGenerator → Compiler → VM`,中间产物是
  **字节码**(不是原生代码),因此运行时是解释执行。
- 静态类型信息在分析阶段确定,支持可选类型标注;`gdscript_warning` / `gdscript_linter` 服务于编辑器提示。
- `modules/gdscript/language_server/` 提供 LSP,`gdscript_cache` 提供跨脚本缓存与循环依赖处理。
- C# 走完全不同的路径(`modules/mono/`):编译为 IL,由 .NET 运行时托管,`ManagedCallable` 桥接回调。

## F9 输入事件流程

```mermaid
sequenceDiagram
    autonumber
    participant OSDS as platform DisplayServer（X11/Wayland/Win/Cocoa/Android/Web）
    participant IN as Input
    participant VP as Viewport(Window)
    participant GUI as GUI(Control)
    participant MI as MainLoop/Node
    participant ACT as InputMap

    OSDS->>OSDS: 原生事件（按键/鼠标/触摸/手柄）
    OSDS->>IN: Input::parse_input_event(ev)
    IN->>ACT: 更新 action 状态（is_action_pressed）
    IN->>IN: 事件累积 / agile flush
    IN->>VP: Viewport::push_input(ev)
    VP->>GUI: 先给 GUI（_gui_input，按 z/focus 顺序）
    alt GUI 未消费
        VP->>MI: Node::_input → _shortcut_input → _unhandled_input
    end
    MI->>MI: 用户代码处理（move_and_slide 等）
```

要点:

- 事件有三个「用户可介入层」:`_input`(最早) → `_gui_input`(Control 专属) → `_unhandled_input`(最后),
  另有 `_shortcut_input`(菜单快捷键)与 `_unhandled_key_input`。
- `set_input_as_handled()` 阻止继续向下传播;正确使用它是避免「输入穿透」的关键。
- `Input` 还维护**状态缓存**(`is_action_pressed`、鼠标位置、摇杆轴),与事件流是两套并行的机制。
- `InputEventScreenTouch/Drag` 经 `Viewport` 的 `physics_object_picking` 转换为 2D/3D 拾取;拾取在物理帧
  里的 `_process_picking` 执行。
- 手柄映射表在构建期由 `input_builders.py` 生成,来源是 `gamecontrollerdb.txt` / `godotcontrollerdb.txt`。

## F10 音频流程

```mermaid

    DRV->>AS: _driver_process(frames, buffer)
    AS->>AS: _mix_step()（按 bus 逆拓扑序混音）
    AS->>BUS: 读取每个 bus 的 volume/mute/solo/send
    AS->>FX: 依次应用效果（重响/延迟/EQ/压缩/…）
    AS->>AS: 3D 播放器做衰减、声像、多普勒（AudioFrame 级）
    AS-->>DRV: 填充输出缓冲
    DRV->>NODE: 播放结束 → finished 信号
```

要点:

- 混音在**音频驱动线程**上跑,与主线程通过无锁队列/原子量通信;因此 `AudioServer` 的多数 API 是
  线程安全的,但**不要在音频回调里做重活**。
- 总线是 DAG(`bus_send`),`_mix_step` 按逆拓扑序计算,`AudioEffect` 按链式顺序串接。
- 3D 空间化参数(距离衰减、声像、混响区域、多普勒)由 `AudioStreamPlayer3D` 每帧更新到
  `AudioServer` 的 playback 上。
- 解码器以模块形式提供(`ogg/vorbis/mp3/theora`),`AudioStream` 的实现决定是否需要提前解码。

## F14 GDExtension 与模块加载

```mermaid
sequenceDiagram
    autonumber
    participant MAIN as Main（各初始化级别）
    participant GDM as GDExtensionManager
    participant LIB as DynamicLibrary（.dll/.so/.dylib）
    participant EXT as 扩展代码
    participant MREG as initialize_modules(level)

    MAIN->>MREG: 调用内建模块的 register_types（编译期决定）
    MAIN->>GDM: initialize_extensions(level)
    GDM->>LIB: 加载 .gdextension 指定的库（open + 解析符号）
    GDM->>EXT: godot_extension_entry（GDExtensionInterface 函数表）
    EXT->>EXT: 注册类、方法、单例（用 C ABI 绑定）
    EXT-->>GDM: 返回初始化结果
    MAIN->>MAIN: 继续下一个初始化级别（CORE→SERVERS→SCENE→EDITOR）
```

要点:

- **内建模块与 GDExtension 使用同一套初始化级别和时间点**,`ModuleInitializationLevel` 的数值与
  `GDEXTENSION_INITIALIZATION_*` 对齐(`modules/register_module_types.h`)。
- 动态库入口有多个:`godot_*_entry` 家族与兼容旧 ABI 的 `godot_gdnative_*`;`gdextension_special_compat_hashes.cpp`
  处理历史版本的方法哈希兼容。
- 扩展只能通过 C ABI 访问引擎,**没有 C++ ABI 兼容性保证**;`--dump-extension-api` 生成的
  `extension_api.json` 是绑定的真源,`--validate-extension-api` 在 CI 中做兼容性校验。
- 模块的开关在构建期由 `modules/*/config.py` 的 `can_build()` 与 SCons 选项决定,
  `modules_enabled.gen.h` 生成 `MODULE_X_ENABLED` 宏。

## F15 关闭与清理

```mermaid
sequenceDiagram
    autonumber
    participant M as Main::cleanup
    participant ML as MainLoop
    participant SC as scene
    participant SV as servers
    participant CORE as core

    M->>ML: main_loop->finalize() 与 SceneTree::finalize()
    M->>ML: memdelete(main_loop)
    M->>SC: uninitialize_modules(EDITOR) → unregister_editor_types()
    M->>SC: uninitialize_modules(SCENE) → unregister_scene_types()
    M->>SV: unregister_platform_apis() / unregister_driver_types()
    M->>SV: uninitialize_modules(SERVERS) → unregister_server_types()
    M->>SV: 释放 rendering_server / display_server / audio
    M->>CORE: uninitialize_modules(CORE) → unregister_core_types()
    M->>CORE: 内存泄漏检测报告（--verbose 时打印）
```

要点:

- 关闭是初始化的**严格逆序**;顺序错误会导致「析构时访问已释放单例」的崩溃。
- `SceneTree::finalize()` 会移除所有节点并发出退出通知,`Node::_exit_tree` 与
  `NOTIFICATION_PREDELETE` 是清理 `RID` 的最后机会。
- 编辑器还会额外做:关闭未保存场景提示、缓存落盘、远程调试断开。
